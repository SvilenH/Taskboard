# Подготовка за защита на Taskboard

Taskboard е приложение за лични проекти, Kanban задачи и файлове. При защитата покажи реалния облачен режим на https://svilen-taskboard.netlify.app. Примерните акаунти и паролите са в частния формуляр за предаване: Alex е администратор, Boyan е обикновен потребител.

## Представяне за около 30 секунди

„Taskboard помага да разделя проект на малки задачи и да проследя напредъка им. Всеки проект има To do, In progress и Done. Задачите имат описание, приоритет, срок и файлове. Използвах HTML, CSS, JavaScript, Bootstrap и Vite, а Supabase предоставя PostgreSQL, вход на потребители и частно файлово хранилище. Правата се проверяват на сървъра чрез RLS.“

Проектът е разработен с Codex по изрично избраната тема. Обясни кои изисквания зададе и как проверявахме резултата. Конкретен пример за отстранен проблем: премахването на файл губеше незаписаните task промени; поправката запазва отворения редактор и въведения текст.

## Демонстрация за около 6 минути

1. **Вход и обзор.** Влез като Boyan. Посочи името и статистиките. Презареди, за да покажеш запазената сесия.
2. **Проект.** Projects → New project. Създай „Course presentation“ с описание. Проектът и трите начални колони се създават заедно в DB транзакция.
3. **Задачи.** Добави „Prepare presentation“ с High приоритет и срок. Редактирай описанието и запази. Добави втора задача, за да покажеш подреждането.
4. **Табло.** Премести задача в Done, презареди и покажи запазената колона и напредъка. С клавиатура можеш да подреждаш чрез стрелките; колоната се сменя и през редактора.
5. **Файлове и филтри.** Качи малък TXT/PDF към задачата. От Files го свали и отвори. Покажи търсене по заглавие, филтър по проект и Done/Open в All tasks.
6. **Права.** Като Boyan отвори `/admin` директно: приложението отказва достъп. Излез и влез като Alex. В Administration покажи потребителите, ролите и проекта на Boyan. Не е необходимо да променяш роли при демонстрацията.
7. **Телефон и код.** На тесен екран покажи Open menu → Close menu / Escape. В GitHub покажи историята в `main`, 10-те HTML entries, SQL migrations, DB диаграмата в README и зелените Actions проверки.

Остави създадения проект до края на защитата. За изтриване използвай потвърждението в приложението. Данните в Demo workspace са локални за браузъра; избери Sign in за доказателство за реалния backend.

## Как минава една операция

Браузърът зарежда отделен HTML entry и `src/main.js` избира page module. Страницата използва общи components и `services/backend.js`. Service-ът извиква Supabase SDK, който изпраща Auth, REST/RPC и Storage заявки. Supabase проверява JWT сесията, SQL правата и RLS.

При „премести задача“ page модулът извиква `moveTask`, service-ът изпраща RPC `tb_move_task`, а PostgreSQL проверява достъпа, заключва проекта и обновява колоната и позициите. UI зарежда запазения резултат. Така показаната подредба съответства на действителната в базата.

## Таблици и връзки

| Таблица | Предназначение |
| --- | --- |
| `tb_profiles` | Име и профил, свързани с `auth.users` |
| `tb_user_roles` | Роля user или admin |
| `tb_projects` | Заглавие, описание, цвят и собственик |
| `tb_stages` | Подредени колони и флаг за Done |
| `tb_tasks` | Задача, проект, колона, позиция, приоритет и срок |
| `tb_attachments` | Име, тип, размер, storage path и връзка със задачата |

Проектът има много колони и задачи, а задачата има много файлове. Composite foreign keys не позволяват задача да използва колона от чужд проект или attachment да сочи несъответстващ project/task. Индексите подпомагат заявки по собственик, колона, подредба и свързани файлове.

## Често задавани въпроси

**Защо има и Auth, и профил?** Auth управлява идентификацията и сесиите. Профилът пази приложни данни, например името. Ролята е в отделна защитена таблица; не се взема от editable signup metadata.

**Достатъчно ли е да скрия admin бутона?** Не. UI guard помага на потребителя, но DB и Storage RLS отказват директни непозволени заявки. Това е проверено с реални заявки от обикновения акаунт.

**Защо publishable key се вижда в браузъра?** Той е предназначен за клиентското приложение. Достъпът до частните записи зависи от JWT и RLS. Secret/service-role ключ не се включва във frontend.

**Защо Storage и `tb_attachments` са отделни?** Storage пази файловите bytes. Таблицата пази metadata и връзката със задачата. При upload с неуспешен metadata запис клиентът опитва да премахне вече качения файл.

**Как се развива schema?** Чрез append-only SQL migrations в `supabase/migrations`, приложени в студентския Supabase. SQL тестът възстановява schema в PGlite и проверява ограниченията и правата. Реалният cloud тест отделно проверява Supabase Auth и Storage API.

**Какво проверяваме автоматично?** GitHub Actions инсталира от lockfile, изпълнява 13 теста и production build. `npm run check:live` проверява публичните адреси и ресурси. UI и реалните cloud проверки са описани в `verification.md`.

**Защо е multi-page?** Всяка основна страница има отделен HTML файл и page module. Нормалните URL адреси поддържат директно отваряне и refresh. Popup се използва за task editor, а основните екрани са отделни страници.

## Практически ограничения

Email confirmation е изключено по избора за курса: адресът трябва да е във валиден формат, но не се проверява собствеността му. Публикуването в Netlify е ръчно. Преди delete приложението почиства Storage; директно SQL изтриване извън приложението не прави автоматично това почистване. Не представяй тези поведения като функции, които проектът не реализира.
